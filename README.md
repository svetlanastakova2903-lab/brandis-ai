# Подбор от AI Brandis — MVP чат + подписка

## Что внутри
- `backend/` — Node.js/Express сервер: принимает диалог, определяет намерение пользователя (бренд ищет
  блогера / блогер ищет бренд-бартер / блогер ищет кросс-промо), делает предфильтрацию баз (если >200
  анкет), вызывает Claude API (`claude-sonnet-4-6`) только с сервера.
- `backend/importCsv.js` — импорт баз блогеров и брендов из выгрузки Tilda (CSV) →
  `backend/data/bloggers.json` и `backend/data/brands.json`.
- `backend/data/bloggers.test.json`, `backend/data/brands.test.json` — тестовые анкеты (используются, если
  `DATA_MODE=test`).
- `backend/data/bloggers.json` — реальная база: 524 блогера из присланного CSV (12 анкет пропущены — не
  было имени/города).
- `backend/data/brands.json` — 2090 брендов/бизнесов из того же CSV (категория "Бренды"), используются
  для сценария «блогер ищет бренд/бартер». Сейчас включён `DATA_MODE=real` — сайт работает на этих
  реальных базах.
- `backend/db.js` — Postgres: схема, подключение, запросы (пользователи, история, платежи, лимиты).
- `backend/billing.js` — лимиты (1 бесплатный поиск → подписка 999₽/мес на 50 поисков → докупка +20 за 299₽),
  жизненный цикл подписки, "прочёсывание" просроченных автосписаний.
- `backend/yookassa.js` — обёртка над API ЮKassa (создание платежей, автосписания по сохранённому способу
  оплаты, проверка вебхуков).
- `backend/telegram.js` — обёртка над Telegram Bot API (deep-link авторизация через `/start <код>`).
- `backend/history.js` — персистентная история диалога по `telegram_id` + сжатие старой истории в саммари
  через Claude Haiku, чтобы стоимость контекста не росла с длиной переписки.
- `backend/test-billing.mjs` — регрессионный тест лимитов/платёжной логики против реального Postgres
  (без обращений к ЮKassa/Telegram/Anthropic). Запуск: `npm test` (нужен `DATABASE_URL`).
- `frontend/chat.html` — **новая** отдельная страница чата (вместо встроенного виджета): авторизация через
  Telegram, персистентная история, лимиты, оплата.
- `frontend/widget.html` — **старый** встроенный виджет для Tilda (без лимитов и биллинга). Оставлен для
  обратной совместимости, пока сайт не переключили на `chat.html` — работает через отдельный, не защищённый
  лимитами эндпоинт `/api/chat` (v1). После перехода на `chat.html` его можно убрать с Tilda и из репозитория.

## Три направления чата
1. **Бренд → Блогер** — бизнес ищет блогера под рекламу (деньги или бартер). Поиск по базе блогеров.
2. **Блогер → Бренд** — блогер ищет бренд для сотрудничества, в том числе бартер (товар/услуга взамен
   рекламы). Поиск по базе брендов.
3. **Блогер → Блогер** — кросс-промо, совместные коллабы, обмен аудиторией. Поиск по базе блогеров с
   фильтром `looking_for: cross_promo_with_blogger`, пользователь исключается из выдачи, если назвал свой ник.

Если из первого сообщения не ясно, кто пишет (бренд или блогер) и что ищет — AI сначала задаёт один
уточняющий вопрос вместо того, чтобы гадать. В каждой рекомендации явно указан формат: 💰 деньги, 🔄 бартер
или 🤝 кросс-промо.

## Важно про реальные данные
В твоей выгрузке (Tilda export) для блогеров нет полей "цена" и "engagement", а для брендов — нет
"бюджета" и типа предложения (деньги/бартер/товар) — эти поля стоят `null` или дефолт "деньги", AI их не
выдумывает. У блогеров также нет данных о `looking_for` (реклама за деньги / бартер / кросс-промо) — по
умолчанию всем проставлено `["paid_collab"]`, это стоит уточнить и актуализировать вручную или через
следующую выгрузку. Контакт блогера = ссылка на соцсеть, собранная из ника + платформы (Инстаграм/Телеграм/
TikTok/VK/YouTube); контакт бренда = телефон, извлечённый из описания анкеты.

Если позже пришлёшь более полную выгрузку (с ценой, ER, бюджетом, типом сотрудничества) — прогони её через
`node importCsv.js /путь/к/файлу.csv`, он пересоберёт `bloggers.json` и `brands.json`. При необходимости
поправь маппинг колонок внутри `importCsv.js` под новый формат.

## Лимиты и подписка
- **Бесплатно**: 1 полностью завершённый поиск (весь диалог до момента, когда бот выдаёт готовую подборку —
  уточняющие вопросы не считаются). Считается по факту вызова инструмента `deliver_recommendations`
  (модель обязана вызвать его вместе с текстовым ответом, когда выдаёт итоговую подборку) — не по числу
  сообщений, это надёжнее, чем парсить текст ответа.
- **Подписка 999₽/мес**: 50 завершённых поисков за расчётный период. Период и его обнуление привязаны
  к дате цикла ЮKassa (дню, когда прошла оплата/автосписание), а не к 1-му числу календарного месяца.
- **Докупка +20 поисков за 299₽** (разовый платёж): доступна только когда лимит подписки в текущем периоде
  исчерпан. Сгорает вместе с обнулением периода подписки.
- Все поля лимитов и статуса — в таблице `users` (`backend/db.js`), привязаны к `telegram_id`.
- Расход input/output-токенов логируется на каждый поиск (`search_events`) и на каждое сжатие истории
  (`summary_events`) — для проверки unit-экономики после запуска.

## Персистентная история и авторизация через Telegram
Чат на `frontend/chat.html` требует привязки Telegram, прежде чем разблокировать диалог:
1. Страница генерирует `session_code`, показывает кнопку-ссылку `t.me/<бот>?start=<session_code>`.
2. Бот получает `/start <session_code>`, бэкенд привязывает `telegram_id` к этой сессии и выдаёт
   постоянный `access_token` (непрозрачный токен, не сам `telegram_id` — так чужой числовой ID нельзя
   использовать, чтобы прочитать чужую историю или статус подписки).
3. Страница поллит `/api/auth/status`, получает `access_token`, сохраняет в `localStorage` и дальше
   шлёт его в заголовке `Authorization: Bearer <token>` на все защищённые эндпоинты.
4. История переписки хранится в таблице `messages` по `telegram_id`. Чтобы стоимость контекста не росла
   с длиной диалога, старая часть истории (всё, кроме последних ~8 сообщений) время от времени сжимается
   в `conversation_summary` через **Claude Haiku** — раз в ~10 новых сообщений или когда их оценочный объём
   превышает ~3000 токенов (см. `backend/history.js`).

## Настройка окружения (нужно для запуска и локально, и на Render)

### 1. База данных — Postgres
В проекте до этой задачи не было БД вообще. Она нужна для лимитов, истории и оплаты, и должна быть
**персистентной** — НЕ бесплатный Postgres на Render (он удаляется через 30 дней). Рекомендуется бесплатный
Postgres на [Supabase](https://supabase.com) или [Neon](https://neon.tech) — данные там не удаляются,
инстанс просто "засыпает" при простое и просыпается на первый запрос.

1. Создай проект на Supabase (или Neon).
2. Settings → Database → Connection string → URI. Скопируй.
3. Впиши в `DATABASE_URL` (и локально в `.env`, и в Render → Environment).
4. Схема создаётся автоматически при старте сервера (`db.initSchema()` в `server.js`) — миграции гонять
   не нужно.

### 2. Telegram-бот
1. Токен бота — от `@BotFather` (`123456:ABC-...`) → `TELEGRAM_BOT_TOKEN`.
2. Username бота бэкенд сам один раз спросит через `getMe()` и закеширует — задавать `TELEGRAM_BOT_USERNAME`
   вручную не обязательно (но можно, чтобы не делать лишний запрос при каждом холодном старте).
3. Вебхук (`https://<адрес бэкенда>/api/telegram/webhook`) регистрируется автоматически при каждом старте
   сервера — вручную ничего дёргать не нужно, достаточно, что задан `TELEGRAM_BOT_TOKEN`.

### 3. ЮKassa
1. `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` — из личного кабинета ЮKassa (сначала тестовые, для проверки).
2. В личном кабинете ЮKassa укажи URL для вебхуков: `https://<адрес бэкенда>/api/billing/webhook`,
   события `payment.succeeded` и `payment.canceled`.
3. Автосписания подписки реализованы вручную (у ЮKassa нет отдельной сущности "подписка"): при первом
   платеже сохраняется `payment_method_id` (`save_payment_method: true`), дальше повторные списания по
   этому ID инициирует сам бэкенд — см. "Как работают автосписания" ниже.

### 4. Публичный адрес
`PUBLIC_BASE_URL` — адрес бэкенда (`https://brandis-ai.onrender.com` на Render), используется для
`return_url` после оплаты и для регистрации Telegram-вебхука.

## Как работают автосписания подписки (важно понимать)
Бесплатный тариф Render "засыпает" после 15 минут простоя — обычный `setInterval` внутри процесса для
этого ненадёжен: если сервис спит, таймер не тикает, и продление не спишется вовремя. Вместо этого
используется "оппортунистическая" схема: на **каждый** входящий запрос к `/api/v2/chat` бэкенд сначала
дёргает `billing.sweepDueRenewals()` — она находит все подписки, чей `subscription_period_end` уже прошёл,
и пытается списать их через сохранённый способ оплаты. То есть любой запрос от ЛЮБОГО пользователя
попутно "прочёсывает" просроченные продления. Если сервис долго не будили — продление спишется с опозданием
при следующем визите (не критично: пользователь всё это время просто продолжает пользоваться подпиской).
При 3 неудачных попытках списания подряд подписка деактивируется (`subscription_status = inactive`).

Если в будущем понадобится точное продление день-в-день без ожидания трафика — можно добавить внешний
cron (например, бесплатный пинг на cron-job.org раз в час на отдельный эндпоинт), либо перевести Render-
сервис на платный always-on тариф. Для MVP это не сделано, чтобы не создавать лишних зависимостей и
затрат до первых реальных подписчиков.

## Запуск локально
```bash
cd backend
npm install
cp .env.example .env
# впиши ANTHROPIC_API_KEY, DATABASE_URL и (по желанию для локальной проверки чата) TELEGRAM_BOT_TOKEN
npm start
```
- Старый виджет: `http://localhost:3000/widget.html`
- Новая страница чата: `http://localhost:3000/chat.html`

Прогнать регрессионный тест лимитов/платежей (нужен доступ к Postgres, локальному или облачному):
```bash
DATABASE_URL=postgres://... npm test
```

## Деплой на Render (бесплатный тариф)
Уже задеплоено: https://brandis-ai.onrender.com

Если нужно пересоздать сервис:
1. Зайди на render.com → New → Web Service → "Public Git Repository".
2. Вставь ссылку на этот репозиторий.
3. Настройки сервиса:
   - Root Directory: `backend`
   - Build Command: `npm install`
   - Start Command: `npm start`
   - Instance Type: Free
4. Environment → добавь все переменные из `.env.example` (`ANTHROPIC_API_KEY`, `DATA_MODE`,
   `PUBLIC_BASE_URL`, `DATABASE_URL`, `TELEGRAM_BOT_TOKEN`, `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`).
5. Deploy. Проверь: `https://brandis-ai.onrender.com/api/health` должен вернуть `{"ok":true,...,"dbConfigured":true}`.

⚠️ Бесплатный тариф Render "засыпает" после 15 минут простоя — первый запрос после паузы может занять
до 30-50 секунд (сервис "просыпается"). Это нормально для MVP (см. также раздел про автосписания выше).

## Вставка в Tilda
Новую страницу чата (`frontend/chat.html`) на Tilda **не встраивают инлайном** — она открывается по
прямой ссылке `https://brandis-ai.onrender.com/chat.html` (или на своём домене/поддомене, если подключишь).
На Tilda нужна просто кнопка/ссылка "Открыть AI-подбор" ведущая на эту страницу — вместо прежнего
встроенного HTML-блока с `widget.html`.

Старый виджет (`frontend/widget.html`) по-прежнему можно вставлять инлайном как раньше (см. историю
этого README) — он работает через отдельный эндпоинт `/api/chat` без лимитов и биллинга. Держать его
имеет смысл только на переходный период.

## Аналитика
- `GET /api/logs` — последние 200 диалогов старого виджета (v1, без биллинга). На проде стоит закрыть
  паролем/токеном.
- Токены на unit-экономику — таблицы `search_events` (основная модель) и `summary_events` (Haiku),
  обе привязаны к `telegram_id`, есть `input_tokens`/`output_tokens` на каждую запись.

## Ограничения текущего MVP
- Предфильтрация — по городу/нише/подписчикам через простые эвристики (ключевые слова в тексте запроса),
  без ML/эмбеддингов — этого достаточно для 500+ анкет и укладывается в контекст модели.
- CORS открыт для всех источников (`cors()` без ограничений) — для продакшена стоит ограничить своим
  доменом.
- Автосписания подписки не гарантированы день-в-день на бесплатном тарифе Render (см. раздел выше) —
  для MVP это осознанный компромисс.
- TOP-бейдж в анкетах и Airtable — не входят в эту задачу.
- Единственный способ авторизации — Telegram (MAX и другие способы не реализованы).
